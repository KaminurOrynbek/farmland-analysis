3.7. Technology Comparison and Selection Rationale
3.7.1. Introduction
The selection of appropriate technologies constitutes a critical design decision in the development of any data-driven system, as it directly determines the performance, maintainability, scalability, and long-term extensibility of the resulting platform. In the context of the farmland analysis web service developed in this research, technology selection decisions were required across five principal system domains: the backend API framework, the machine learning library, the geospatial processing toolchain, the satellite data access platform, and the frontend visualization stack.
Each selection decision was evaluated against a consistent set of criteria: computational performance and throughput, support for asynchronous or parallel execution, ease of integration within the Python-centric system architecture, availability of relevant pretrained models or geospatial data sources, quality of documentation and community support, and open-source licensing. The purpose of this section is to document and justify each technology selection through structured comparative analysis, providing a transparent account of the design rationale underlying the implemented system.
3.7.2. Backend Framework
The backend of the system serves as the central orchestration layer responsible for handling all incoming API requests, coordinating geospatial data processing, managing communication with external satellite data platforms, and invoking the machine learning inference pipeline. Three Python-based web frameworks were evaluated: FastAPI, Flask, and Django REST Framework (DRF).
Flask is a minimalist microframework that offers a low barrier to entry and considerable flexibility in application structure. Its synchronous request handling model, however, becomes a limiting factor in applications that must coordinate multiple I/O-bound operations — such as satellite imagery retrieval, file upload processing, and external API calls — within a single request lifecycle. Achieving asynchronous behaviour in Flask requires third-party extensions, which introduce additional configuration overhead and reduce architectural coherence.
Django REST Framework provides a comprehensive, batteries-included environment for API development, including built-in authentication, serialization, and database ORM support. However, DRF's monolithic design philosophy introduces significant structural overhead that is unnecessary for a lightweight, stateless geospatial processing API. Its synchronous execution model presents the same I/O concurrency limitations as Flask, and its extensive built-in feature set imposes a non-trivial performance penalty relative to more focused frameworks.
FastAPI was selected on the basis of four principal advantages. First, it provides native support for asynchronous request handling through Python's asyncio library, enabling concurrent processing of I/O-bound operations without blocking the event loop. Second, it achieves request throughput performance significantly outperforming Flask and DRF under concurrent load. Third, it incorporates automatic generation of interactive OpenAPI-compliant documentation, which facilitates API testing and integration verification during development. Fourth, its use of Pydantic models enforces strict data validation at the API boundary, reducing the risk of malformed data propagating through the processing pipeline.

3.7.3. Machine Learning Framework
The machine learning component requires a framework capable of supporting transfer learning workflows, providing access to pretrained convolutional neural network architectures, and enabling flexible model customisation. Three frameworks were evaluated: PyTorch, TensorFlow, and Keras.
TensorFlow is a production-grade deep learning framework developed by Google, widely adopted in industrial deployments due to its mature serving infrastructure and support for distributed training. However, TensorFlow's API surface is substantially more complex than PyTorch's for tasks involving custom training loops or model architecture modification, which are central to the transfer learning methodology of this research.
Keras provides a high-level API that significantly simplifies model construction and training for standard use cases. Its ease of use, however, comes at the cost of reduced flexibility in scenarios requiring fine-grained control over training procedures — such as implementing differential learning rates across layer groups during fine-tuning — which are essential to the methodology applied in this study.
PyTorch was selected due to its dynamic computational graph paradigm, which allows the model's computational structure to be modified at runtime, facilitating interactive debugging and rapid prototyping. The torchvision.models module provides direct access to ResNet-50 pretrained on ImageNet, simplifying the transfer learning workflow. Furthermore, PyTorch is the dominant framework in current academic remote sensing and computer vision research, ensuring the availability of up-to-date reference implementations and community support.

3.7.4. Geospatial Processing Tools
The geospatial processing component of the system must handle two distinct data types: vector data (field boundary polygons in GeoJSON format) and raster data (multispectral satellite imagery). Three tools were evaluated: GeoPandas, Rasterio, and GDAL.
GDAL (Geospatial Data Abstraction Library) is the foundational C-based library underlying most open-source geospatial software, providing comprehensive support for an extensive range of vector and raster data formats. However, GDAL's low-level C API exposes considerable complexity when used directly from Python, requiring verbose boilerplate code for operations that higher-level libraries handle transparently. Its steep learning curve makes it less suitable for rapid application development within a research prototype context.
GeoPandas extends the Pandas DataFrame model to support geospatial data types through integration with the Shapely geometry library. It provides an intuitive, Pythonic interface for vector data operations — including geometry validation, coordinate reference system (CRS) reprojection, area computation, and centroid extraction — that maps naturally to the tabular data processing patterns common in Python scientific computing. GeoPandas was selected for all vector data operations in this system.
Rasterio, built on the GDAL abstraction layer, provides a high-level Python interface for raster data I/O, spatial masking, band extraction, and coordinate transformations. Its context-manager-based file handling and NumPy-native array operations make it well-suited for the spatial clipping and band arithmetic operations required in the vegetation index computation pipeline. Rasterio was selected for all raster data operations.

3.7.5. Satellite Data Platforms
Two external platforms were evaluated for satellite imagery access: Google Earth Engine (GEE) and Sentinel Hub.
Google Earth Engine is a cloud-based planetary-scale geospatial analysis platform that provides programmatic access to a petabyte-scale archive of satellite imagery, including the complete Sentinel-2 and Landsat catalogues. Its Python API supports complex spatial queries, temporal filtering, cloud masking, and image compositing operations within the cloud environment, eliminating the need for local storage or high-performance computing infrastructure. Access is free for research and educational purposes, which is a decisive practical advantage in an academic project context.
Sentinel Hub is a platform optimised for high-performance delivery of processed satellite imagery tiles via RESTful APIs. Its primary strength lies in efficient, low-latency rendering of imagery tiles in web-compatible formats, making it highly suitable for integration with browser-based mapping libraries such as Leaflet.js. Its analytical processing capabilities are more limited compared to GEE, and its free tier imposes usage constraints that would limit large-scale backend processing.
In the implemented system, both platforms are used in a complementary manner: GEE serves as the primary backend data processing and imagery retrieval platform, while Sentinel Hub is used for frontend satellite basemap tile rendering. This hybrid approach leverages the analytical strengths of GEE and the rendering performance of Sentinel Hub without requiring full reliance on either platform's limitations.

3.7.6. Frontend Technologies
The frontend layer must support dynamic map-based user interaction, efficient rendering of geospatial overlays, and seamless consumption of the backend JSON API. Three JavaScript frameworks were evaluated for the UI component: React, Vue.js, and Angular. Three web mapping libraries were additionally evaluated: Leaflet.js, Mapbox GL JS, and OpenLayers.
Vue.js offers a gentle learning curve and a clean reactivity model, making it well-suited for smaller applications. However, its ecosystem for geospatial visualization is less mature than React's, and its adoption in production-grade data-intensive web applications is more limited. Angular provides a comprehensive, opinionated framework with strong TypeScript integration, but its complexity and steep initial configuration overhead are disproportionate for a focused single-page analytical application.
React was selected on the basis of its component-based architecture, which enables modular and reusable UI construction, and its efficient virtual DOM reconciliation algorithm, which minimises re-rendering overhead during frequent map state updates. Its extensive ecosystem supports all functional requirements of the frontend.
Mapbox GL JS offers superior visual quality through WebGL-accelerated vector tile rendering but requires a commercial API key for full functionality. OpenLayers provides comprehensive geospatial functionality but carries a larger API surface and steeper learning curve. Leaflet.js was selected for its lightweight runtime footprint, intuitive API, broad tile provider compatibility — including direct integration with Sentinel Hub endpoints — and sufficient feature set for rendering GeoJSON overlays and analytical result layers.

3.7.8. Conclusion
The comparative analysis presented in this section demonstrates that the selected technology stack provides the optimal balance of performance, flexibility, development efficiency, and open-source accessibility for the requirements of the farmland analysis platform. Each selection decision is grounded in a structured evaluation against consistent criteria, ensuring that the architectural choices are both technically justified and academically defensible.
The resulting technology combination — FastAPI, PyTorch, GeoPandas, Rasterio, Google Earth Engine, Sentinel Hub, React, and Leaflet.js — forms a coherent, modular, and extensible foundation for the implemented system, supporting both the current prototype scope and prospective future development of the platform.
